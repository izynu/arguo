Arguo is maintainer-led with consensus, at least for now. A young project does not need a committee on day one, but it does need visible decisions.

Decision process. Routine changes land through pull requests reviewed by a maintainer. Significant decisions, such as new providers, schema changes to the ledger or catalog, or anything affecting the security posture, are opened as issues first, argued in the open, and resolved when maintainers reach consensus. If consensus fails, the lead maintainer decides and records the reasoning in the issue.

How maintainers are added. A maintainer is nominated by an existing maintainer, typically after sustained, high-quality contributions to code, catalog, or docs. The nomination is a public pull request that adds the person to the maintainers list, approved by consensus of current maintainers. Maintainers can step down at any time, and additions and departures stay visible in repository history.

Transparency requirements. Decisions happen in public channels: issues, pull requests, the changelog, and the worklog. Security reports are the exception and stay private until coordinated disclosure allows publication. Release notes must match what actually shipped, and the roadmap must not promise dates the project does not control.

This model is a starting point, not a constitution. As contributors arrive, the project will revisit it in public, with the same rule that applies to the code: changes land through review, and the reasoning is written down where others can find it.
